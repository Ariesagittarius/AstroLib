# AstroLib 自动化测试套件与类型守卫架构交接文档

## 1. 建设背景与重构动因

在本次架构升级前，AstroLib 存在以下痛点：
1. **测试脚本碎片化与割裂**：在 `scripts/` 目录下散落了 14 个命名与调用方式各异的独立测试脚本（如 `test-latex-export.mjs`、`test-comment-stripper.mjs`、`verify_notices.mjs` 等），缺乏统一的断言体系、统一测试收集器与结构化结果输出；
2. **缺乏统一 CI/CD 质量门禁**：无法在 GitHub Actions 或本地提交时以统一命令并行执行自动化回归，容易漏检深层断言；
3. **TypeScript 类型覆盖不均**：部分单例配置与核心算法散落在 `.mjs`，存在大量 `any` 隐式传递与缺失类型声明，代码重构时缺乏编译期静态类型保护；
4. **视窗层级存在未声明魔数**：样式表中偶见硬编码的大型 `z-index`，破坏了 `layers.css` 令牌层级规范。

遵循 **“系统本身干净可复用为要务”、“支持破坏性重构”、“无遗留死代码”** 的原则，本项目全面引入 **Vitest + TypeScript 严格模式**，构建了现代四层测试金字塔架构与 CI 门禁体系。

## 2. 四层测试金字塔架构 (The 4-Tier Test Pyramid)

全站测试统一收敛在项目根目录的 `tests/` 下，划分为 4 个分层：

```
        ▲
       / \         Tier 4: System Tests (物理排版与多端集成，~8s)
      /   \        tests/system/*.test.ts - Typst 内存 PDF、XeLaTeX 双通字体编译
     /     \
    /       \      Tier 3: Acceptance Tests (业务端到端验收，~1.5s)
   /         \     tests/acceptance/*.test.ts - 导出联动、LaTeX 闭合、AST 交叉引用
  /           \
 /             \   Tier 2: Contract Tests (架构契约与卫生守卫，~300ms)
/               \  tests/contract/*.test.ts - public 零污染、Window Layers、Schema
-----------------
  Tier 1: Unit     tests/unit/*.test.ts - 纯算法、状态机、AI 异常、Slug 鲁棒性 (~200ms)
```

### 2.1 各分层职责与用例分布

| 层级 | 目录 | 测试性质 | 耗时 | 测试套件与目标 |
| :--- | :--- | :--- | :--- | :--- |
| **Tier 1** | `tests/unit/` | 纯逻辑单元测试 | ~200ms | 6 套测试 / 17 用例：<br>• `comment-stripper.test.ts`：AST 智能注释剥离安全与无死循环<br>• `slug.test.ts`：路由 slug 与 cleanSlug 标准化<br>• `natural-sort.test.ts`：中英文混合自然排序与章号对齐<br>• `notice-engine.test.ts`：全站通知规则引擎状态机<br>• `ai-error.test.ts`：AI 多厂商（Gemini/DeepSeek）统一错误包装<br>• `ai-gemini-tools.test.ts`：Gemini 端侧 MCP 工具参数与元数据解析 |
| **Tier 2** | `tests/contract/` | 架构契约测试 | ~300ms | 6 套测试 / 15 用例：<br>• `public-hygiene.test.ts`：`AGENTS.md` Rule 5 契约，守护 `public/` 严禁产生任何编译残留<br>• `window-layers.test.ts`：全局 173 个源文件视窗层级扫描，严禁散落 >= 50 的 z-index 魔数<br>• `katex-metrics.test.ts`：KaTeX 官方度量偏移补丁完整性<br>• `features-schema.test.ts`：Feature Registry 唯一数据源 Schema<br>• `collections-schema.test.ts`：图书合集注册表 Schema 契约<br>• `typography-presets.test.ts`：学术排版预设 4 套严格收敛与无 Variable Font 契约 |
| **Tier 3** | `tests/acceptance/` | 业务端到端验收 | ~1.5s | 5 套测试 / 35 用例：<br>• `export-acceptance.test.ts`：Chapter / Exercise 导出设置联动、静态资源 chapter-scoped 解析、数字资源学术排版<br>• `latex-export.test.ts`：Jinwen-XU/homework 试卷与练习册全量生成、LaTeX 语法平衡与环境闭合<br>• `typst-export.test.ts`：LaTeX 转换为 Typst 语法、全量题库零占位符残留<br>• `crossref-ast.test.ts`：Remark/Rehype 构建期交叉引用 AST 下沉与徽章注入<br>• `exercises-dataset.test.ts`：全量题目数据集合法性与非空结构校验 |
| **Tier 4** | `tests/system/` | 物理引擎与系统集成 | ~8s | 3 套测试 / 5 用例：<br>• `typst-full-generation.test.ts`：多章节抽样在内存中通过 Typst 原生 Node 编译器渲染多页 PDF<br>• `typography-specimen.test.ts`：调用本地 XeLaTeX 执行双通物理编译与字体嵌入验证（环境自适应）<br>• `ui-stacking.test.ts`：CSS 视窗层级单调递增性与 Chromium 运行环境探测 |
| **合计** | `tests/` | **全自动化测试套件** | **~8.7s** | **20 套测试 / 72 个测试用例全部绿灯通过** |

## 3. 核心架构不变量与设计准则

### 3.1 Zero Side-Effects (零磁盘污染原则)
- 任何测试均不得向 `public/`、`src/` 或受版本控制的目录写入临时测试文件（严格契合 `AGENTS.md` Rule 5 公共目录卫生守卫）；
- 物理编译（如 XeLaTeX）必须在系统临时目录（`os.tmpdir()`）中执行独立隔离，并在测试生命周期的 `afterAll` 钩子中完全清理；
- Typst 编译测试直接在内存中执行字节流断言（`compiler.pdf({ mainFileContent })`），零磁盘写入。

### 3.2 Environment Defensive (环境自适应优雅降级)
- 依赖宿主机环境（如 XeLaTeX 编译器、Edge/Chrome 无头浏览器）的高级系统测试，统一由 `tests/helpers/env-detector.ts` 集中探测；
- 当本地或云端 CI 容器未安装 XeLaTeX 或图形浏览器时，测试套件通过 `it.skip()` 自动优雅跳过，保证在标准 Node.js CI 镜像下 100% 绿灯通过，杜绝产生环境误报。

### 3.3 100% Strict TypeScript Type Coverage (严格类型覆盖)
- 统一重构核心配置与工具为原生 TypeScript（`collections.config.ts`、`features.config.ts`、`notices.config.ts`、`themes.config.ts` 等），提取了规范的领域模型接口（`src/types/`）；
- 全套测试与生产代码均在 `tsconfig.json` 的 `strict` 模式下经过严格校验，执行 `npm run check:types` 保持 **0 errors**。

## 5. NPM 命令与 CI/CD 流水线

### 5.1 常用执行指令速查

```bash
# 1. 运行核心日常自动化测试 (Unit + Contract + Acceptance，约 1.5 秒完成)
npm test

# 2. 单独运行指定层级测试
npm run test:unit        # Tier 1 单元测试 (~200ms)
npm run test:contract    # Tier 2 契约测试 (~300ms)
npm run test:acceptance  # Tier 3 业务验收测试 (~1.5s)
npm run test:system      # Tier 4 系统级集成测试 (含 PDF 物理编译)
npm run test:all         # 全量 20 套测试 (~8.7s)

# 3. 监听模式 (日常边写边测)
npm run test:watch

# 4. 严格类型检查 (tsc --noEmit，0 错误门禁)
npm run check:types

# 5. 全站质量门禁 (提交前推荐运行：类型检查 + 核心测试)
npm run check:all
```

### 5.2 GitHub Actions CI 流水线 (`.github/workflows/ci.yml`)

项目配置了 3 个并行/级联阶段的自动化质量门禁：
1. **`static-analysis`**：执行 `npm run check:types`，确保没有任何类型错误；
2. **`automated-tests`**：执行 `npm test`，运行金字塔前三层（Unit、Contract、Acceptance）；
3. **`system-integration`**：执行 `npm run test:system`，在 CI 环境运行 Typst 编译器排版集成测试。

## 6. 新增测试编写 SOP 与扩展指引

开发者在向项目贡献新功能、新算法或新导出格式时，请遵循以下分层指南：

1. **纯计算/文本转换逻辑**：放入 `tests/unit/`。要求测试纯函数，零网络、零外部依赖；
2. **架构约束与 Schema 定义**：放入 `tests/contract/`。编写对配置单一真实源、公共目录无污染或设计令牌的契约断言；
3. **复杂业务链路与解析流水线**：放入 `tests/acceptance/`。利用真实或 Mock 数据验证输入输出完整性与语法闭合（可借助 `tests/helpers/latex-validators.ts` 进行语法平衡校验）；
4. **涉及外部编译器或系统环境**：放入 `tests/system/`。引入 `tests/helpers/env-detector.ts` 检查外部依赖，并对临时文件进行生命周期管理。
